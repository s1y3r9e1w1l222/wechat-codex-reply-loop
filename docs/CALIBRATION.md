# 本机校准：开发者操作说明

适用于 0.2.0 开发版：中文微信、440 × 956 点竖屏。校准只建立列表标记与唯一名称映射，不再逐个进入头像、个人资料或免打扰详情。`calibrate` 读取当前列表，输出空映射和 `verified: false`，不会覆盖已有文件。

## 先保存未读，再进入会话

允许名单定义范围，不是逐个打开的任务。先扫描列表，只把允许、确有未读且列表未显示免打扰的会话持久入队，再进入对应聊天。没有未读且没有已保存任务的会话不打开。

预览也会清除红点，因此必须走同一持久队列，不能先手工打开全部允许会话做校准。预览后重启会复用已保存的输入和队列；不会因为红点消失就丢掉原任务。校准前已被清除且没有记录的未读不能从聊天历史中猜测恢复。

## 列表与会话绑定

1. 由设备所有者明确选择允许联系人或群，为每个会话分配稳定本地 ID。
2. 确认列表中使用的完整、唯一显示名称；群名包含的空格、表情、大小写均需照实记录。一个 ID 对应一个名称，重名时先由用户调整备注，不用坐标猜测目标。
3. 在当前列表确认未读数量／标记、免打扰文字或 `bell_off_regular` 图标、完整列表底部及搜索框位置。免打扰只从列表筛选，不进入详情页确认。
4. 将明确允许的群 ID 写入 `group_keys`。运行时在真正处理未读时才进入聊天：单聊标题精确匹配名称，群聊匹配名称及 `(人数)` 后缀。
5. 标记能力和布局实际确认后再启用有关校准标志。首次运行保持预览，检查队列与草稿后再显式 `run --send`；更改映射或群类型须重新预览。

同一次设备事务内复用从唯一列表行建立的绑定；读取上下文、输入后检查及发送后检查都只核对当前聊天，不重复打开头像。发送前保留标题、消息末尾、最新输入和精确草稿检查。

私有结构示意（示例中的名称和标志不能直接复制启用）：

```json
{
  "list_bottom": 868,
  "viewport": [440, 956],
  "bundle_id": "com.tencent.xin",
  "muted_marker_verified": false,
  "list_region_complete": false,
  "identities": {
    "本机核对的唯一备注": "contact_a",
    "本机核对的完整群名": "group_a"
  },
  "group_keys": ["group_a"],
  "verified": false
}
```

旧校准文件中的 `profile_signatures` 和 `identity_probes` 仍可读取，运行时不再执行这些头像／详情路径。真实名称、历史校准身份及手机观察都属于本机数据，禁止提交到 Git。

## 已确认的结构与边界

- 消息列表 Cell 包含名称、未读数量／标记、预览和时间。只有完整位于列表底部之上的行参与处理；截断树只有在同一 observation 的完整缓存数量核对通过后才重建。多页扫描仍需两遍一致；跨页发现重复会话 ID 时不视为唯一对象。
- 重启后若先恢复草稿或核对不确定发送，会在同一手机锁内先完成列表扫描，再绑定会话；不会跳过跨页重名检查。
- 聊天消息的 `Other` 标签以发送者开头，`我,` 为己方。群聊保留发言者，图片、语音等不冒充文字输入。发送成功须有唯一新增的己方文本气泡、没有失败标记，并且输入框为空。
- 群成员昵称含 ASCII 逗号可能使标签分隔不明确；只要后续出现媒体标记，就保守按非文字处理，不把可能的图片或语音当文字交给 AI。
- 输入框从已确认的聊天输入区域聚焦，读取实际焦点 value；发送不限定输入法，只使用可唯一识别的“发送”或 `send` 按钮／键，通过元素点击，不直接使用键盘报告的相对坐标。
- 最新位置需有滚动条 `100%` 证据。初次未读数量未知、历史前后无法唯一对齐、存在人工草稿或浮层时保留任务并提示处理；不能把整个历史当作新输入。
- 此次修复已增加合成闭环。先前辅助真机发送不等同于修复版本连续无人值守通过，见 [验证记录](VALIDATION.md)。

## 其他 App

该校准约定仅适用于微信。青藤之恋、积目和 Soul 后续适配不要求逐联系人手工校准，目前真实入口仍返回 `adapter_not_available`。见 [多 App 说明](MULTI_APP.md)。
